## 0. Главное в десяти строках

1. ads-monitor — **внутренний инструмент одной команды**, не SaaS: один общий пароль, без пользователей, ролей, тарифов и биллинга.
2. **Источник данных один — публичная Meta Ad Library**, которую читает настоящий headless Chromium (Playwright) без логина: берётся JSON внутреннего GraphQL страницы. Google Ads Transparency, TikTok и официальный Ad Library API **не подключены**.
3. Собирается **только то, что команда явно отслеживает** (трекеры по page ID, имени страницы или домену лендинга). Обзора рынка, категорий и «всех брендов ниши» нет.
4. Единица ленты — **группа креативов**: объявления с одним и тем же главным файлом (sha256 картинки или постера видео) показываются одной плиткой с «×N · K pages».
5. Метрики успешности: **точный охват ЕС и Великобритании** с историей замеров, **место по показам** (rank) внутри запроса трекера, **число копий**, отметка **`<100` показов**, **дни показа**. Spend и impressions нет нигде; для США точных цифр нет вообще.
6. Четыре метки-сигнала: Scaling, Top by impressions, Long-running, Pulled fast. Дельт за 7/14 дней, выживаемости, графиков и единой оценки нет.
7. Поиск — только подстрока (`ILIKE`) по имени страницы, тексту, адресу лендинга и имени конкурента. Поиска по смыслу, по картинке и по речи нет.
8. **Нет совсем:** AI/LLM-функций, MCP, публичного API, воронок и пейволов, экспорта, алертов и уведомлений, избранного и коллекций, сохранённых видов, аналитических страниц и графиков.
9. Ядро сбора работает и хорошо покрыто тестами (по документам 5 196 автотестов и 21 e2e); CI нет.
10. Главные риски: недокументированный GraphQL Meta и закреплённые `doc_id`, блокировка IP, один воркер и один браузер (низкая пропускная способность), рост диска без очистки, бэкап на том же хосте.

### 1.3. Деплой

- Весь стек — один `docker-compose.yml`; порты публикуются только на `127.0.0.1` (`docker-compose.yml:42,64,145`). Секреты из одного `.env`.
- README описывает деплой на VPS и схему «web, база и файлы на VPS, воркер дома через SSH-туннель» (`README.md:151–236`). По бэклогу деплой на VPS — открытая задача OPS-01; фактически стенд работает на машине владельца. Развёрнут ли VPS, из кода не видно.
- **CI нет** (каталога `.github` нет; задача QA-01). Образов из CI и отката по тегу нет (OPS-12).
- Бэкап: `pnpm backup` — `pg_dump` и инкрементальное зеркало медиа в `BACKUP_DIR` (`tools/src/backup.ts`); по умолчанию на том же хосте (OPS-02 открыта).

### 1.4. Поток данных

```
web (команда @ads/db: строка + pg-boss job в одной транзакции)
  -> очередь browser -> worker: Chromium -> Meta Ad Library (GraphQL JSON)
     -> processBatch: ad_snapshots, ads, ad_trackers, ad_media, ad_observations
     -> очередь media.download -> CDN Meta -> MinIO (sha256) -> ads.creative_key
  scheduler.tick (cron */5): плановые прогоны трекеров + не более одного прогона details (охват)
web читает через lib/dal.ts -> запросы @ads/db
```

Источник сменный по контракту `AdSource` (`packages/core/src/types.ts:109–123`: `search`, `resolvePages?`, `details?`), но реализаций две: `meta-web` и тестовая `fake` (`SOURCE_MODE=fake`, `apps/worker/src/sources.ts`).

### 2.1. Как идёт сбор (`packages/sources/meta-web/src/source.ts`)

- Chromium открывает страницу Ad Library без логина; слушатель ответов ставится до `goto`. Первая страница приходит двумя путями (JSON в HTML или первый ответ `/api/graphql/`), дедуплицируется по списку `ad_archive_id`.
- Следующие страницы грузятся только настоящим `mouse.wheel` (`source.ts:498`) с паузой `SCROLL_DELAY_MS` 2–6 с. Первая прокрутка часто ничего не даёт: ~20 с потери на поиск (DATA-03, принято).
- Первый `403` — JS-проверка Meta, не ошибка. `/login` → `login_wall`, `/checkpoint` → `challenge_failed` (`source.ts:125–133`).
- `PROXY_URL` задаёт прокси браузеру и загрузке медиа; состояние браузера (`storageState`) хранится в `BROWSER_STATE_DIR`.
- Сырые узлы выдачи сохраняются (`ad_snapshots.payload`) при каждом изменении содержимого; нормализатор версионируется, есть CLI `renormalize` для переразбора.

### 2.2. Виды прогонов (`runs.kind`)

| Вид | Что делает | Кто ставит |
|---|---|---|
| `resolve` | поиск страниц по имени через typeahead рекламодателей Meta (до 15 страниц, ранжирует `rankPageCandidates`) | пользователь в форме трекера |
| `baseline` | первый сбор активных объявлений трекера; «новым» ничего не помечает | создание трекера |
| `scheduled` | плановая проверка | `scheduler.tick` |
| `manual` | «Run now» | пользователь |
| `archive` | «Load archive»: остановленные объявления (`active_status=all`); без лимита объявлений; вне ЕС почти ничего не приносит | пользователь |
| `details` | проверка охвата: запрос деталей объявления пачкой | только `scheduler.tick` |

### 2.3. Очереди и расписание (`packages/db/src/boss.ts`)

- `browser`: строго по одному заданию; приоритеты resolve 30 > baseline/scheduled/manual 20 > archive 10 > details 5 (`boss.ts:8`); `retryLimit: 2` (`boss.ts:43`), у `details` — 0 (`boss.ts:89`). Между заданиями пауза `JOB_GAP_MS` 30–90 с.
- `media.download`: `retryLimit: 5`, backoff, истечение 600 с (`boss.ts:48`); параллельность `MEDIA_CONCURRENCY` = 4; файл, который человек запросил вручную, идёт с приоритетом 10.
- `scheduler.tick`: cron `*/5` (`boss.ts:49`): прерывает осиротевшие прогоны, ставит `scheduled` для трекеров с прошедшим `next_run_at`, затем не более одного `details` (`apps/worker/src/jobs/scheduler-tick.ts:104,175`).
- Частота трекера: в UI 6, 12, 24 или 48 часов (по умолчанию 24); команда принимает 1…720 (`packages/db/src/commands/rules.ts:11–12`). Следующий запуск со случайным сдвигом ±20 % (`rules.ts:24–31`).

### 2.4. Лимиты прогона (`apps/worker/src/runner/limits.ts:58`, `.env.example`)

| Параметр | Значение по умолчанию |
|---|---|
| `trackers.max_ads` | 100 на прогон (10…5000), свой у каждого трекера |
| `RUN_MAX_PAGES` / `RUN_TIMEOUT_MIN` | 40 страниц / 15 мин |
| `BASELINE_MAX_PAGES` / `BASELINE_TIMEOUT_MIN` | 100 страниц / 30 мин |
| `IMPRESSIONS_PASS_ADS` | 50 объявлений сверх `max_ads`, не более 10 страниц (`limits.ts:36`) |
| `DETAILS_DAILY_LIMIT` / `DETAILS_BATCH` | 300 запросов за 24 ч / 25 за прогон |
| `DETAILS_DELAY_MS` / `DETAILS_MIN_GAP_MIN` | 4–8 с перед запросом / 60 мин между прогонами |
| `MEDIA_MAX_BYTES` / `MEDIA_TIMEOUT_MS` | 500 МБ / 300 с |

Следствие для сравнения: пропускная способность мала по замыслу. При 300 запросах в сутки охват 30 000 объявлений нельзя перепроверять ежедневно; повторные замеры идут с адаптивным интервалом (§4.3).

### 2.5. Защита от блокировки

- `challenge_failed` / `login_wall` ставят **весь источник** на паузу 1 → 3 → 6 → 24 ч и стирают cookies (`apps/worker/src/source-state.ts:4–5`).
- Правило «подозрительно пустой ответ» (`apps/worker/src/runner/empty-policy.ts`): трекер, у которого раньше были объявления, получил ноль → `unexpected_empty`.
- Проверка формата: ответы валидируются zod-схемами; несоответствие → `schema_drift` (не повторяется), `errors[]` GraphQL → `network` (повторяется).

## 3. Модель данных (`packages/db/src/schema.ts`)

Иерархия проще, чем у AdSpyLab: **конкурент → трекеры → объявления → группа креатива**. Сущностей «бренд с доменами и воронками», «концепт-семья», «воронка», «экран» нет.

| Таблица | Суть | Ключевые поля |
|---|---|---|
| `competitors` | конкурент (аналог бренда, только имя) | `name`, `archived_at` |
| `trackers` | сохранённый поиск | `criterion_type` (`page_id` / `page_name` / `domain`), `criterion_value`, `page_id`, `country` (одна или `ALL`), `languages[]` (до 10), `interval_hours`, `enabled`, `max_ads`, `media_type` (`all`/`image`/`video`), `media_kinds[]`, `next_run_at`, `baseline_done_at`, `baseline_pages` |
| `runs` | прогон | `kind`, `status`, `reason`, `complete`, `covered_since`, счётчики `pages`, `ads_seen`, `ads_new`, `filtered_out`, `normalize_errors`, `reported_count`, `ranked`, `error`, `error_sample`, `rank_error`, `params`/`result` (для resolve) |
| `ads` | объявление, одно на `ad_archive_id` | см. ниже |
| `ad_trackers` | связь объявление ↔ трекер | `first_run_id`, `last_run_id`, `matched_host`, `rank`, `rank_at`, `rank_fresh_until` |
| `ad_snapshots` | сырой узел Meta при каждом изменении | `content_hash`, `payload` (jsonb), `fetched_at` |
| `ad_media` | файл объявления | `slot`, `kind` (`image`/`video`/`video_preview`), `file_key`, `source_url`, `url_expires_at`, `status` (`pending`/`done`/`failed`/`expired`/`skipped`), `sha256`, `requested_at` |
| `media_objects` | уникальный файл | `sha256`, `mime`, `bytes` |
| `ad_reach` | один замер охвата | `checked_at`, `eu_reach`, `uk_reach`, `eu_breakdown`, `uk_breakdown` (страна × возраст × пол) |
| `ad_observations` | наблюдение объявления в прогоне | `low_impressions`, `collation_count`, `rank` |
| `source_state` | пауза источника | `paused_until`, `pause_level`, `empty_tracker_ids`, `last_reason` |
| `worker_heartbeat` | пульс воркера | `beat_at` |
| view `ad_status` | статус объявления | `active` / `not_seen` / `inactive` (`migrations/0001_ad_status_view.sql`) |

### 3.1. Поля объявления (`ads` и `AdRecord`, `packages/core/src/types.ts:150–175`)

- Идентичность и страница: `ad_archive_id`, `page_id`, `page_name`, `pageProfileUri`, `pageIsDeleted`.
- Содержимое: `displayFormat` (IMAGE, VIDEO, DCO, CAROUSEL…), `publisherPlatforms[]`, `body`, `title`, `caption`, `linkUrl`, `linkDescription`, `ctaText`, `ctaType`, `links[]` (все ссылки, включая карточки карусели), `assets[]`.
- Время: `start_date`, `end_date`, `is_active`, `first_seen_at`, `last_seen_at`.
- Копии: `collation_id`, `collation_count` (число копий по Meta), `copies_grew_at`.
- Охват: `eu_reach`, `uk_reach` (последние известные), `reach_checked_at`, `reach_due_at`, `reach_interval_hours`, `reach_grew_at`.
- «Новое»: `is_new`, `new_at`.
- Группа: `creative_key` (sha256 главного файла), `group_key` (генерируемое: ключ креатива или `ad:<id>`).

**Чего в данных нет:** spend, impressions (числом), таргетинг, страны показа, язык объявления как поле, транскрипт, OCR, топик, формат «UGC / talking head», эмбеддинги, категория бренда.

### 3.2. Метрики и как они считаются

| Метрика | Источник | Расчёт |
|---|---|---|
| Статус | view `ad_status` | `inactive`: Meta сказала «не активно». `not_seen`: все живые трекеры объявления после него успешно просканировали нужный период и не увидели. Иначе `active` |
| Дни показа (Running) | `runningDaysSql`, `packages/db/src/queries/feed-signals.ts:116–124` | от `start_date` до сегодня (активное), до `end_date` (остановленное) или до дня `last_seen_at` (не видно); минимум 1 |
| Охват ЕС / UK | прогон `details` | точное число из блока прозрачности Meta; история в `ad_reach`; на плитке одно число — сумма ЕС и UK |
| Место по показам (rank) | второй проход прогона с `sort: impressions` | место **группы копий** среди групп, прошедших фильтр трекера; хранится на паре объявление–трекер; свежо `max(7 дней, 2 интервала трекера)` (`feed-signals.ts:50–57`) |
| Число копий | `collation_count` узла Meta | как сказала Meta; рост штампует `copies_grew_at` |
| Копии в группе | наши данные | число сохранённых объявлений с тем же `group_key` и число их страниц |
| `<100` показов | поле узла Meta | булева отметка в `ad_observations.low_impressions`; в ленте отдельно не показывается |

Важные оговорки (из `docs/overview.md`): место считается внутри запроса одного трекера по накопленным показам во всех странах, места разных трекеров между собой не сравнимы; для США нет ни показов, ни расхода.

### 3.3. Метки-сигналы (`SIGNAL_RULES`, `feed-signals.ts:31–44`)

| Метка | Правило |
|---|---|
| Scaling | число копий или охват выросли за последние 7 дней |
| Top by impressions | свежее место 1–10 в области списка (трекер / конкурент / все) |
| Long-running | активно 30 дней или дольше |
| Pulled fast | остановлено менее чем за 7 дней |

На плитке одна метка, в этом порядке приоритета. Группа несёт лучшие сигналы своих копий.

## 4. Функции

Состояние: **Работает** — реализовано и покрыто тестами; **Частично**; **Нет** — в коде отсутствует.

### 4.1. Конкуренты — работает

- **Где:** `apps/web/app/(main)/competitors/*`, `app/actions/competitors.ts`, `packages/db/src/commands/competitors.ts`, `queries/competitors.ts`.
- **Пользователь:** список конкурентов с числом трекеров и новых креативов; создание (имя уникально); архивирование вместе с трекерами; страница конкурента с вкладками Ads (лента в области конкурента) и Trackers.
- **Ограничения:** у конкурента только имя. Нет категории, списка доменов, списка страниц, профиля с графиками и KPI (PRD-04 в бэклоге).

### 4.2. Трекеры — работает

- **Где:** `app/(main)/trackers/new`, `trackers/[id]`, `app/actions/trackers.ts`, `tracker-page.ts`, `packages/db/src/commands/trackers.ts`, `rules.ts`.
- **Критерии:** Page ID; имя страницы (поиск → карточки страниц с категорией, подписчиками Facebook и Instagram, верификацией → каждая отмеченная страница становится трекером); домен лендинга (включая поддомены, с предупреждением о пропусках).
- **Настройки:** страна, языки, частота, лимит объявлений, какие объявления собирать (все / картинки / видео), какие файлы скачивать, включён/выключен.
- **Действия:** Run now, Load archive, Create a copy, Archive, массовое включение/выключение и запуск (`setTrackersEnabledAction`, `enqueueTrackerRunsAction`), последние 20 запусков.
- **Правила:** критерии поиска неизменяемы после создания; дубль живого трекера у того же конкурента запрещён; физически ничего не удаляется.
- **Нет:** автоподсказки новых страниц конкурента из найденных объявлений (PRD-01); автообнаружения новых рекламодателей в нише.

### 4.3. Сбор охвата ЕС и UK — работает

- **Где:** `apps/worker/src/jobs/details.ts`, `apps/worker/src/reach/*`, `packages/sources/meta-web/src/details*.ts`, `packages/db/src/queries/reach-budget.ts`.
- **Как:** запрос `AdLibraryV3AdDetailsQuery` отправляется изнутри открытой вкладки Ad Library; `doc_id` закреплён (`packages/sources/meta-web/src/constants.ts:13`), заменяется переменной `META_DETAILS_DOC_ID`.
- **Очерёдность:** две полосы — первые проверки (до 40 % пачки) и повторные (`apps/worker/src/reach/schedule.ts:19–31`).
- **Адаптивный интервал** (`schedule.ts:1–11,54–65`): 24 ч, пока цифры меняются; удваивается до 14 дней, пока стоят; объявление без охвата — через 7 дней, затем до 28 дней; остановленное объявление получает последний замер и больше не проверяется.
- **Пользователь:** охват на плитке и в таблице, история замеров и разбивка в открытом объявлении; блок «Reach checks» в статусе сбора (израсходовано из лимита, сколько ждёт, когда возобновится).

## 7. Технические риски и что может работать не так

### 7.1. Зависимость от Meta (самое хрупкое)

| Риск | Где | Последствие |
|---|---|---|
| Недокументированный GraphQL: формат ответа может смениться | `packages/sources/meta-web/src/schemas.ts`, `parse.ts`, `normalize.ts` | прогоны `failed`/`schema_drift`; данные перестают обновляться до правки кода. Смягчение: сырые снапшоты и `renormalize` |
| Закреплённый `doc_id` запроса охвата | `packages/sources/meta-web/src/constants.ts:13` | после смены Meta проверки охвата падают; три нечитаемых ответа подряд завершают прогон (`apps/worker/src/jobs/details.ts:39`). Лечится переменной окружения и рестартом воркера |
| Закреплённый `doc_id` typeahead | `constants.ts:20` | поиск страниц по имени падает сразу. Поведение Meta на устаревший id вживую не проверено: возможен `login_wall`, который ставит на паузу весь сбор (по `CLAUDE.md`) |
| Блокировка IP, проверка, требование входа | `apps/worker/src/source-state.ts:4–5`, `source.ts:125–133,488` | весь источник на паузе до 24 ч; резервного источника нет |

| Первая прокрутка не грузит страницу 2 (DATA-03) | `source.ts:498,527` | ~20 с на каждый поиск; при росте числа трекеров прогоны ближе к лимиту времени |
| Счётчик Meta не равен списку | `runs.reported_count` | `count > 0` при пустых `edges` — нормальный пустой ответ, не потеря страницы |
| `media_type=image` у Meta возвращает 0 | `packages/sources/meta-web/src/url.ts` (`MEDIA_TYPE_PARAM`) | решено отображением в `image_and_meme`; любая сборка URL в обход сломает трекеры «только картинки» |
